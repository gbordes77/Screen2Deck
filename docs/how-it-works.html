01 Ce que fait Screen2Deck

Tu prends une capture d'écran de ton deck dans MTG Arena, MTGO, sur Moxfield, ou tu photographies tes cartes papier. Screen2Deck te renvoie une deck list propre, validée carte par carte contre Scryfall, exportable instantanément en MTGA, Moxfield, Archidekt ou TappedOut.

TL;DR — Image → texte → noms de cartes canoniques → fichier d'import, en moins de 3 secondes sur le chemin rapide.

Le projet est une application web full stack : un backend Python/FastAPI qui orchestre l'OCR et la validation, un frontend Next.js/TypeScript pour l'upload et le résultat, une base PostgreSQL + un cache Redis, et une option de bot Discord qui expose les mêmes commandes.

02 Le problème qu'on résout

Un joueur de Magic tombe régulièrement sur un deck intéressant (replay de tournoi, screenshot d'un streamer, photo d'un ami) et veut l'importer dans son client préféré pour l'essayer.

Manuellement, ça demande :

  • Lire les 60 + 15 noms de cartes sur une image basse résolution
  • Les retaper sans faute de frappe (Fable of the Mirror-Breaker, Esika's Chariot, Fire // Ice…)
  • Gérer les split cards, les DFC, les adventures, les cartes avec apostrophe
  • Vérifier chaque nom contre une base à jour pour ne pas avoir des erreurs à l'import
  • Remettre dans le bon format selon la plateforme cible

Soit 15 à 20 minutes par deck et beaucoup d'erreurs. Screen2Deck fait tout ça automatiquement en quelques secondes.

03 Le pipeline en 7 étapes

Quand tu cliques sur "Analyser", voici ce qui se passe dans l'ordre :

1

Upload et validation de l'image

Le frontend envoie le fichier à POST /api/ocr/upload. Le backend vérifie le type MIME, la taille (max 8 MB par défaut), les dimensions, et calcule un hash SHA-256 pour la déduplication. Si le même hash a déjà été traité, on renvoie le résultat en cache sans relancer le pipeline.

2

Création d'un job asynchrone

Un job_id UUID est généré, stocké dans Redis (job_storage), et renvoyé au frontend. Le frontend commence à poller GET /api/ocr/status/:jobId avec un backoff progressif (500 ms → 2 s).

3

OCR — deux chemins possibles (voir section 04)

Le backend décode l'image avec OpenCV, puis choisit entre le chemin rapide (LLM Vision avec JSON structuré) et le chemin legacy (EasyOCR multi-variantes). Le choix dépend du flag VISION_PRIMARY et de la disponibilité d'une clé GEMINI_API_KEY.

4

Parsing en sections

Sur le chemin legacy, une regex convertit chaque ligne OCR 4 Lightning Bolt en CardEntry(qty=4, name="Lightning Bolt"). Sur le chemin rapide, le modèle a déjà rendu directement un JSON {main:[{qty,name}], side:[...]}, donc on saute le parser.

5

Résolution Scryfall (batch)

Tous les noms bruts partent en un seul appel à POST /cards/collection (75 cartes max par requête). Les cartes manquantes retombent sur /cards/named?fuzzy= + rapidfuzz local contre le bulk data. Le résultat est une NormalizedDeck dont chaque entrée a un scryfall_id stable.

6

Business rules (MTGO 60+15 & sanity check)

apply_mtgo_land_fix redécoupe un flat main-board de 75 cartes en 60 + 15 quand l'OCR a raté le marqueur sideboard. validate_and_fill log des warnings si la taille du deck est anormale (moins de 60 main-board, plus de 15 sideboard).

7

Export à la demande

Le résultat DeckResult est stocké dans Redis avec TTL. L'utilisateur clique sur un format (MTGA, Moxfield, Archidekt, TappedOut) et le frontend appelle POST /api/export/:format qui sérialise la NormalizedDeck dans la syntaxe cible.

04 Les deux chemins OCR

L'étape 3 du pipeline peut emprunter deux routes totalement différentes, choisies par le flag VISION_PRIMARY.

Chemin rapide — recommandé

Vision LLM en primaire

Un seul appel à Gemini 3.1 Flash-Lite (ou Claude Haiku 4.5 en fallback) avec une contrainte de schéma JSON.

  • 1. Encode l'image en JPEG base64
  • 2. Appel client.models.generate_content avec response_mime_type=application/json et un response_schema typé
  • 3. Le modèle renvoie directement {main:[{qty,name}], side:[...]} — pas de parsing texte, pas de regex
  • 4. Le prompt spécifie les règles MTGO 60+15, le format // pour split/DFC/adventure, les suffixes x2/x3 de MTGA

Gain : p95 ~2,7 s, coût < $0,0001 par image, précision +3 à 5 points vs le chemin legacy.

Chemin legacy — toujours dispo

EasyOCR multi-variantes

Utilisé quand Vision est désactivé, rate-limited, ou a renvoyé une réponse inutilisable.

  • 1. preprocess_variants génère 4 images (originale, denoisée, binarisée, sharpened)
  • 2. Super-résolution 4× si la largeur est < 1200 px
  • 3. run_easyocr_best_of lance EasyOCR sur chaque variante avec early-stop si la confiance moyenne ≥ 0,85 et 20+ lignes détectées
  • 4. Si mean_conf < 0,62, on bascule quand même sur Vision LLM (version texte plat, pas structuré)
  • 5. parse_deck_sections applique une regex sur les spans pour extraire qty + name

Pourquoi le garder : fonctionne sans clé API, résilient aux pannes Gemini/Claude, fournit un filet pour les benchmarks offline et le mode low-connectivity.

Fail-over automatique — Si le chemin rapide est activé mais que Vision échoue (quota free tier épuisé, provider 429, JSON malformé), le backend retombe sur le chemin legacy dans le même handler, sans que l'utilisateur voie une erreur.

05 Pourquoi Scryfall est la clé

Magic a plus de 25 000 cartes distinctes, certaines avec des apostrophes, des tirets, des accents, des noms qui partagent un préfixe. L'OCR seul ne peut pas garantir que "Thoughtsieze" (typo) devienne "Thoughtseize" (canonique). C'est là que Scryfall intervient.

Trois niveaux de résolution

  1. Batch exact (< 500 ms) — Un seul appel à POST /cards/collection avec jusqu'à 75 identifiants. Scryfall fait le matching insensible à la casse et aux accents, renvoie data[] pour les trouvés et not_found[] pour les autres.
  2. Fuzzy local (0 ms) — Si tu as hydraté le bulk data (python backend/scripts/download_scryfall.py), le client utilise rapidfuzz contre les ~30 000 noms en mémoire pour corriger les typos OCR sans toucher au réseau.
  3. Fuzzy online (~100 ms) — Dernier recours /cards/named?fuzzy= pour les cas vraiment vicieux (un nouveau set juste sorti, un nom non-anglais).

Conformité User-Agent

Depuis 2024, Scryfall exige un header User-Agent descriptif sous peine de rate-limiting agressif. Screen2Deck s'annonce comme Screen2Deck/2.4 (+https://github.com/gbordes77/Screen2Deck).

Invariant « ALWAYS_VERIFY_SCRYFALL » — Le flag ALWAYS_VERIFY_SCRYFALL=true est codé en dur dans la configuration recommandée. Aucune carte ne sort du pipeline sans avoir été validée contre Scryfall. Pas de "on fait confiance à l'OCR".

06 Le cas spécial MTGO 60+15

MTGO (Magic: The Gathering Online) exporte ses decks de tournoi sous forme d'image qui liste les 75 cartes en une seule colonne, sans marqueur Sideboard. L'OCR voit donc juste 75 cartes alignées, sans savoir où couper.

business_rules.apply_mtgo_land_fix gère ce cas précis :

  • Si le total main-board > 60 cartes ET sideboard vide, on déclenche la redistribution
  • On accumule les cartes jusqu'à atteindre MIN_MAIN = 60
  • La carte qui franchit la frontière est splittée : partiellement dans le main, le reste dans le sideboard
  • Tout ce qui dépasse 60 va en sideboard

Exemple concret : si l'OCR renvoie 64× Island en flat, le résultat devient 60× Island main + 4× Island sideboard. Ce n'est pas un "vrai" deck de tournoi (personne ne sideboard des basics), mais c'est la meilleure approximation structurelle quand on n'a pas d'autre info. Le chemin rapide Vision évite ce problème entièrement : le modèle sait lire les layouts MTGO et rend directement la bonne segmentation dans le JSON.

07 Architecture complète

Quatre gros blocs, quatre dépendances externes, une base de données et un cache. Rien de magique.

08 Formats d'export

Quatre cibles d'import, tous sérialisés depuis la même NormalizedDeck.

MTGA
Format Magic Arena — 4 Lightning Bolt une ligne par carte, Sideboard séparateur.
Moxfield
Syntaxe moxfield.com — copie-colle direct dans l'import.
Archidekt
CSV avec colonnes Count,Name,Categories — échappement correct pour Knight, Errant.
TappedOut
Format TappedOut.net — 4x Lightning Bolt.

L'endpoint POST /api/export/:format prend la deck en JSON et renvoie du text/plain. Les 4 formats partagent le même validator d'entrée et le même modèle NormalizedDeck, donc ajouter un cinquième format (Deckstats, TCGplayer, …) est ~20 lignes de code.

10 Performance et coût

Les chiffres ci-dessous sont des projections, pas des mesures. Ils viennent du modèle d'un agent perf-engineer, de l'arithmétique tokens × prix Gemini, et de recherches web sur les benchmarks publics. Tant que make smoke + un vrai benchmark n'ont pas tourné sur cette branche, traite ces chiffres comme des targets, pas comme des preuves.

Important — Le fichier DISCLAIMER.md à la racine du repo liste exactement quels chiffres sont vérifiés et lesquels sont projetés, avec la commande précise pour les mesurer.
Métrique Chemin rapide (Vision) Chemin legacy (EasyOCR)
p50 latence projeté ~1,2 s ~2,0 s
p95 latence projeté ~2,7 s ~4,1 s
Précision card name projeté 90–97 % 85–94 %
Coût par image projeté ~$0,0001 (après free tier) 0 $
Dépendance réseau vérifié Gemini + Scryfall Scryfall seul
Cache hit rate non vérifié 50–80 % (ancien README) 50–80 % (ancien README)

Origine des chiffres — p50/p95 : modèle de l'agent performance-engineer sur un screenshot MTGA 1920×1080 typique. Précision : estimation qualitative OCR-research agent. Coût : arithmétique basée sur les tarifs Gemini 3.1 Flash-Lite ($0,25/$1,50 par 1M tokens) et ~258 tokens input + ~300 tokens output par image — ignore les surcoûts de verbosité du modèle, donc probablement sous-estimé de 30-50 %. Cache hit rate : copié du README existant, jamais re-mesuré sur ce refactor.

Pour passer ces chiffres de "projeté" à "mesuré", il suffit de lancer :

# 2. Pré-hydrater le cache Scryfall
python backend/scripts/download_scryfall.py

# 3. Smoke test end-to-end (boot + upload + verify + export)
make smoke

# 4. Benchmark complet contre le validation_set
make bench-day0

11 Sécurité

Les mesures actives en production :

  • JWT via PyJWT — l'ancienne dépendance python-jose 3.3.0 était affectée par CVE-2024-33663 (algorithm confusion) et CVE-2024-33664 (JWT decompression bomb). Migration complète vers PyJWT ≥ 2.8.0, chaque jwt.decode exige un claim exp.
  • IDOR protection — GET /api/ocr/status/:jobId vérifie que le caller authentifié est bien le propriétaire du job (match sur user_id). Les jobs anonymes restent lisibles par UUID, comme avant, mais un job créé par un user authentifié est invisible aux autres.
  • Upload hardening — Validation du type MIME (magic bytes), taille max 8 MB, dimensions max, sanitisation du nom de fichier, décodage OpenCV en flux borné pour résister aux décompression bombs.
  • Rate limiting — /api/ocr/upload 10 req/min/IP, /api/ocr/status 60 req/min/IP, /api/export/* 20 req/min/IP. Basé IP avec sliding window.
  • Secrets hors code — docker-compose.yml exige ${POSTGRES_PASSWORD:?} et ${JWT_SECRET_KEY:?}, compose fail-fast si les variables ne sont pas définies. k8s/secrets.yaml ne contient que des placeholders __REPLACE_ME__, à override via External Secrets ou Sealed Secrets en production.
  • CI guard anti-secrets — .github/workflows/security-checks.yml échoue si n'importe quel credential par défaut (postgres:postgres, changeme, your-super-secret, dev-secret-key-change-in-production) réapparaît dans l'arbre.
  • CORS restrictif — CORS_ORIGINS est une liste blanche, credentials: true seulement pour les origines connues.
  • Anti-Tesseract guard — contrainte dure : Tesseract n'est jamais installé ni importé. CI scanne chaque commit pour vérifier.

12 Comment le lancer

Développement local (recommandé)

Le .env à la racine du repo doit contenir au minimum POSTGRES_PASSWORD, JWT_SECRET_KEY (32+ caractères via openssl rand -base64 32), et GEMINI_API_KEY (clé gratuite sur aistudio.google.com/app/apikey). 

# Dépendances : Docker + Docker Compose

# 1. Pré-hydrate le cache Scryfall (évite rate-limiting Scryfall sur le premier run)
python backend/scripts/download_scryfall.py

# 2. Start du stack complet
make up              # = docker compose --profile core up -d

# 3. Vérif santé
curl http://localhost:8080/health
# → {"status":"healthy"}

# 4. Ouvre le frontend
open http://localhost:3000

# Tests E2E une fois le stack up
make test-online

# Logs
make logs            # = docker compose logs -f backend webapp

Configuration minimale du .env

# REQUIS — compose fail-fast sinon
POSTGRES_PASSWORD=           # openssl rand -hex 16
JWT_SECRET_KEY=              # openssl rand -base64 32

# Vision LLM primary (recommandé)
VISION_PRIMARY=true
GEMINI_API_KEY=              # aistudio.google.com/app/apikey — gratuit
GEMINI_MODEL=gemini-3.1-flash-lite-preview

# Optionnel — fallback secondaire (nécessite facturation Anthropic)
ANTHROPIC_API_KEY=
ANTHROPIC_MODEL=claude-haiku-4-5

# Settings OCR (défauts raisonnables)
ENABLE_VISION_FALLBACK=true
OCR_MIN_CONF=0.62
ALWAYS_VERIFY_SCRYFALL=true

# Scryfall (10 req/s officiel)
SCRYFALL_API_RATE_LIMIT_MS=100

Endpoints principaux

  • POST /api/ocr/upload → renvoie {jobId}
  • GET /api/ocr/status/:jobId → {state, progress, result}
  • POST /api/export/:format avec la deck en body → text/plain
  • GET /health → health check pour load balancers
  • GET /metrics → exports Prometheus (OCR latency, cache hit rate, vision fallback rate, errors)
  • POST /api/auth/login / POST /api/auth/register → JWT + refresh token (optionnel)
Astuce — Les 4 exporters sont de simples fonctions Python qui prennent une NormalizedDeck. Ajouter un format (Deckstats, TCGplayer, TappedOut avec métadata, …) tient en ~20 lignes dans backend/app/exporters/.
